EditH architecture
without the secrets.

The public architecture documentation explains how the deployed pieces communicate while intentionally excluding tokens, private keys, credentials and internal infrastructure details.

Architecture

GitHub ↓ Vercel — public frontend / Flask web layer ↓ Railway — Discord bot + private control API ↓ Discord + Firebase-backed application data

Discord integration

The Discord bot uses discord.py with full intents and persistent UI views. Slash commands and interaction views execute server-side with Discord's permission and role hierarchy checks.

Dashboard

The Vercel application maintains the browser session and proxies authenticated requests to Railway using a private API key. The browser does not receive that control key.

Authentication

Dashboard credentials are stored in the existing Firebase-backed credential records. Discord OAuth is used by the verification flow, while the web dashboard uses the issued credentials/session.

Security model

Dashboard actions include the actor identity in the server-to-Railway request. Railway resolves that Discord member and re-checks the required permission before mutating a server.

Analytics

The bot calculates live server/member/channel/role metrics and publishes selected public counters to Firebase for the Vercel landing page.

Scaling & limitations

Vercel handles public web traffic and Railway keeps the long-lived Discord process. The system depends on Discord API availability, bot permissions, Firebase availability and Discord role hierarchy.

Private infrastructure

API keys, Discord tokens, Firebase service-account credentials, OAuth secrets and private environment variables are deliberately not documented here.
